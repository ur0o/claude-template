# 仕様書管理 (specification)

## このスキルの役割

プロジェクトの仕様を「対話しながら確定させ、確定したそばからファイルに書き残す」ためのスキル。仕様は一度に全部決めようとせず、トピックごとに小さく質問し、答えが出るたびに `specification/` 配下のMarkdownへ反映する。各トピックの仕様書は常に「今の正」を表すドキュメントであり変更履歴ではないので、変更時は古い記述を書き換える(追記ではなく上書き)。変更履歴そのものは `specification/CHANGELOG.md` に一本化して記録する(後述)。

## モード判定

まずユーザーの発言が「新規策定」か「変更」かを判定する。

- **新規策定トリガー**: 「仕様を決めます」「仕様書を作成して」「仕様を作ります」など、これから仕様を決めていきたいという宣言。`specification/` が存在しない、または空の場合も新規策定として扱う。
- **変更トリガー**: 「仕様を変えます」「〜の仕様を変更したい」など、既存の仕様への変更の宣言。

判定が曖昧なとき(例: `specification/` に一部ファイルはあるが全トピックは埋まっていない状態で「仕様を決めます」と言われた場合)は、既存ファイルの状況を一覧してユーザーに「続きから決めるか」「特定のトピックを決め直すか」を確認する。

## 新規策定フロー

以下の3トピックを **この順番で** 1つずつ確定させる。まとめて質問を並べず、1トピックにつき対話を数往復して詰めてから次に進む。

1. プロダクトの目的・機能 → `specification/01-purpose-and-features.md`
2. 画面デザイン・画面遷移などのUI → `specification/02-ui-and-screens.md`
3. 開発に使う言語・技術スタック → `specification/03-tech-stack.md`

各トピックについて:

- 未確定な点は質問・提案・選択肢の形でユーザーに投げる。具体的な選択肢を出せる質問(例: 「認証方式は独自実装 / OAuth のどちらにしますか」)は AskUserQuestion ツールを使い、推奨案があれば1番目の選択肢にして「(推奨)」を添える。自由記述が必要な質問(例: 「このプロダクトの目的を一言で言うと?」)は通常のテキストで聞く。
- 1つの答えが出るたびに、それを踏まえて次の疑問点を聞く。ユーザーが「あとはお任せします」「そちらで決めて」と言ったら、妥当なデフォルトを提案し確認を取ってから確定させる。
- そのトピックについて実用上十分な情報が揃ったら、対応するファイルを書く(後述の「ファイル構成とフォーマット」を参照)。書いたらユーザーに簡潔に確認を求め、OKが出たら次のトピックに進む。
- 前のトピックで確定した内容と矛盾する提案をしない。次のトピックに入る前に必要なら前のファイルを読み返す。

## 変更フロー

1. **変更対象の特定**
   - 起動時のユーザー発言に対象が明示されている場合(例: 「UIの仕様を変えます」「決済機能の仕様を変更したい」)は、それに対応する既存ファイルを特定してすぐ着手する。ファイル名や見出しだけでなく本文も見て、どのファイルが該当するか判断する。
   - 明示されていない場合は、まず `specification/` 配下の既存ファイルを一覧し、AskUserQuestion でどの仕様を変更するか確認する(選択肢は既存ファイルのトピック名 + 「新しいトピック」)。
   - 該当する既存ファイルがない場合は新規トピックとして扱い、`specification/` 内の最大の連番+1を使ったファイル名で新規作成する(例: 既存が01〜03なら `04-<内容を表す英語スラッグ>.md`)。
2. **変更内容の確定**
   - 対象ファイルを読み、現状の記述を踏まえた上で「何をどう変えたいか」を質問する。変更の余地がある点は選択肢や提案を出し、ユーザーに選んでもらう。
   - 変更が他のトピックのファイルにも影響する場合(例: UI変更が機能追加を伴う)、影響先のファイルも更新対象として扱い、ユーザーに確認の上で更新する。
3. **保存**
   - 変更が確定した時点で即座に対象ファイルを編集する(Editツールで該当箇所を書き換える。全文書き直しが必要なほど大きい変更でなければ差分編集を優先する)。すべての変更が終わってからまとめて保存する、ということはしない。
   - 同じタイミングで `specification/CHANGELOG.md` にも変更履歴を追記する(書式は後述の「CHANGELOG.mdの書式」を参照)。**新規策定フローでは CHANGELOG.md は書かない** — 対象は「既存仕様への変更」のみ。

## ファイル構成とフォーマット

- 保存先はリポジトリルート直下の `specification/` ディレクトリ。存在しなければ作成する。
- 1ファイル1トピック。ファイル名は `<連番2桁>-<内容を表す英語スラッグ>.md`。連番は既存ファイルの続き。
- 各ファイルは概ね以下の構成にする:
  - `# <トピック名>` の見出し
  - 確定した仕様を箇条書き・文章で記述
  - 内容の理解を助ける mermaid 図を最低1つ含める(```mermaid コードブロック)。図の種類はトピックに応じて選ぶ:
    - 目的・機能: 機能同士の関係や主要なユーザーフローを表す `flowchart` や `mindmap`
    - UI・画面遷移: 画面遷移を表す `stateDiagram-v2` または `flowchart`。各画面の要素・レイアウトは mermaid で表現しきれないため、図の前後に文章で補足する
    - 技術スタック: フロントエンド/バックエンド/インフラなどの構成を表す `flowchart` や `graph`
- 仕様書は「今の正」のみを載せる。変更履歴や検討過程は書かず、変更時は該当箇所を上書きする。

## CHANGELOG.mdの書式

`specification/CHANGELOG.md` は仕様**変更**のみを記録する(新規策定時は書かない)。日付ごとに見出しでまとめ、各変更を1行の箇条書きで追記する。

```
## (日付)
- (変更内容の概要) [(カテゴリ)]
```

- 日付は `YYYY-MM-DD` 形式で、変更を確定した当日の日付を使う。
- カテゴリは変更が及ぶ範囲を表す短い語(例: UI、DB構成、使用ライブラリ、機能、API など)。複数のトピックにまたがる変更は複数行に分けて書く。
- ファイルは新しい日付が上に来るように並べる(先頭に追加)。
  - 今日の日付の見出しが既にファイル先頭にある場合は、新しい見出しを作らずその見出しの箇条書きに追記する。
  - 今日の日付の見出しがまだない場合は、ファイル冒頭に新しい `## (今日の日付)` 見出しを追加し、その下に箇条書きを書く。
- ファイルが存在しない場合は、最初の変更時に新規作成する。

## 注意点

- 質問は一度に大量に投げない。ユーザーが答えやすいよう、トピック内でも小さい単位に分けて聞く。
- 決定事項は都度ファイルに反映する。「全部決まってから最後にまとめて書く」をしない — これは要件(変更のたびに自動保存)を満たすためであり、対話が長時間・複数セッションにわたっても既に決まった分が失われないようにするため。
- 既存の仕様と矛盾する回答が来た場合は、それが意図的な変更なのか確認してから上書きする。
- このスキルはテンプレートリポジトリの一部として配布され、これを元にした様々なプロジェクトで再利用される。特定プロジェクト固有の内容(プロダクト名や機能名など)をこのファイル自体に書き込まない。
